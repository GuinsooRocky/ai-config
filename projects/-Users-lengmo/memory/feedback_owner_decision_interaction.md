# owner 拍板交互口径

四条同源：owner 要的是推进，不是被反复确认。适用边界——
- **默认不设门**：带 1 个推荐直接走，只有**不可逆 / 真钱 / 首曝光**才停下来问。
- **owner 明说「挨个问」时例外**：一次一题、纯文本、答完再下一题，不用多题表单。
- **owner 问「哪种最好」不是把拍板权交给我**：他开口问了就要给答案（结论 + 理由 + 前提），再等他选。

## 不设门：带 1 个推荐直接走，不列 A/B、不给待验清单、收尾不列「待你拍」

### 带 1 个推荐方向走，不在抽象里让用户选

> 本节已提级 `~/.claude/CLAUDE.md` 写码行为守则（「有多种理解时带 1 个推荐直接走，只有不可逆的分叉才停下问」），「该不该问」的细则在 `~/.claude/judgment-rubrics.md`。这里只留原始口径一句：**用户要在产物里反馈，不在文字里被 grill**；实现型任务的方案对齐是那条之外的例外（见 [[feedback_task_execution_cadence]] 第 1 段）。

### 让你"做个 loop/自动化"时别堆前置闸把人卡住

用户叫"开个 loop / 把这批做完"时，**别用一串 gate-check + AskUserQuestion 菜单把他拦在门口**——他要的是吞吐，不是被反复确认。正确姿势：把 sane default 焊进去（取数口径照已有对称模式、设计岔口当场拍合理值）直接跑（workflow/ultracode），真有岔口在执行中 inline 抛出，而不是开跑前列三道选择题。安全(只改本仓不碰镜像/禁写桩/测试当 back-pressure)悄悄兜住就行，别拿出来当门槛念。

用户原话（被我用 loop-forge 前置闸 + 选择题挡住后）："做个loop 这么难？那就开个ultracode"。这跟 [[feedback_task_execution_cadence]] 的"按改动规模分级"不冲突——分级是给我自己定深浅，不是拿去问用户。也跟 [[feedback_loop_needs_backpressure_first]] 不冲突：那条要的是「上 loop 前得有可机械判定的 back-pressure」，闸该自己焊进去悄悄兜住，**闸 ≠ 摆给用户的菜单**。

### 别主动建议停下 / 收尾

不要主动说"今晚到这里" / "太晚了" / "先休息" / "明天接着做" / "简单的先做剩下的明天" —— 用户没明确叫停就继续。落档 / 复盘只在用户明确说停时才提。

用户原话："你不要再一直说我就到这里了，因为我要我没告诉你停你还是要怎么样"。

### 别给「待验清单」（2026-08-10 合并自 feedback_no_pending_verification_lists）

交付改动时不要输出「待验清单」，也不要用「这几条还没验，验完再决定下一步」当理由拖住后续工作。

**Why:** 用户原话「没验证的改动就是伪命题 因为 我一直在验证 我不说你可以默认我验证了」。他是边改边点的，每轮都在真机/浏览器上过一遍；我列清单等于要求他重复汇报已经做过的事，还顺带把「等你验完」变成不动手的借口。同一轮他还说「一定要动 只有动了 做成真正的链路了 才能看出新问题」——链路不完整时的「谨慎分批」对他是负价值，半成品暴露不出真问题。

**How to apply:** 改完直接说改了什么、为什么；要提醒就只提**具体现象**（「书还在飞那 210ms 里底边可能多一道暗边，看到了跟我说」），不要罗列成表格式的验收清单。沉默 = 通过。需要他配合的只剩我拿不到的运行时事实（控制台读数之类），那时精确到一句话、一个数字。相关 [[feedback_runtime_bug_dont_loop_static]]。

### 灵感稿不挂「待 owner 确认所指」（2026-08-28 合并自 feedback_ideas_need_no_owner_signoff）

写灵感稿（soliloquy `docs/prd/ideas/` 这类）时，遇到用户一句话没展开的题目，**按最合理的理解直接写完**，不在文档里立「⚠ 这词有两种所指，待 owner 确认」这种门，也不在回复里当待拍项抛回去。

**Why:** 2026-08-28 落「公告系统」灵感，我摆了「平台公告 vs 创作者公告」让他选，被顶：「你觉得一个灵感要我自己确认什么吗」。灵感的价值在于把想法接地到仓里的实况（现有代码有什么、跟哪条红线撞、坑在哪），不在口径精确；要确认所指等升格成 PRD 再说。在灵感阶段设门，等于用不可逆事的规格去要求完全可逆的事。

**How to apply:** 理解写在抬头一行（「按 XX 这层意思写的」），正文照写不设条件。真正该停的门槛不变：对外承诺变更、不可逆迁移、花钱——灵感稿一个都不沾。用户补充所指后直接重写，别追问第二轮。相关 [[feedback_dont_declare_infeasible]]。

### 验收报告末尾的「待你拍」清单也是设门（2026-09-11）

集成验收收尾时，我把三件套裁判标成「尾巴 / 交 owner 拍」的条目原样转成 6 条「待你拍」（本地怎么定义、第 4 个候选模型留不留、要不要补跨仓契约闸、旧面板 403 码要不要一起改、回退按钮禁用手感、解析器闭集），被顶：「你在说啥 你自己思考啊啊啊」。六条没有一条是不可逆、真钱或首曝光，全是我该带推荐直接拍的。

**Why:** 子 agent（裁判）写「交 owner 拍」是它的权限边界，不是我的；主对话是集成者，裁判递上来的口径题到我这里就该决掉。「给闸修闸离目标句两步」这类顾虑按开工三问是**说出来再动**，不是拿去问他。

**How to apply:** 收尾报告只留两类：① 已拍并已做/正在做的决定（一句一条）；② 我拿不到的运行时事实（真库迁移、亲点、部署）。子 agent 报告里的「待 owner 拍」先过一遍「是否不可逆/真钱/首曝光」，不是就自己拍、动手、报结果；是的才带推荐上交，且一次只上真正的那一两条。

### 文档写「待拍」≠ 还没拍：上交前先翻当天提交（2026-09-12）

soliloquy GEO 现状汇报时，我照现行策略和 09-11 改向文档把「公开名」当唯一待拍项上交，被顶「不对呀，我刚做完 SEO……可以用跟 SEO 一样的名字」——同一天 01:19 另一个 SEO 会话提交的 `站外提交素材.md` 早已统一用 Soliloquy Live，只是没回写策略文档。

**Why:** 多会话并发推进时，策略/台账里的「待拍」经常比同日新产物滞后；照旧文档上交等于让 owner 重答一遍他刚答过的题。

**How to apply:** 要上交任何「待 owner 拍」前，先 `git log origin/main --since=<前一天>` 扫当天提交，再 `git grep` 这个待拍项的关键词看同目录新文档是否已按某个答案落地；落地了就当已拍处理，并把滞后的文档当场回写。

## owner 说「挨个问我」= 一次一题、对话里问、答完再下一题

owner 要拍板时说「挨个问我」，意思是**一次一题、对话里问、他答完再下一题**。2026-09-11 我把 4 题塞进一个 AskUserQuestion 表单被当场打断（「你看看我的反馈呢」）。

**Why:** 表单一次摊四题他没法逐题想；而且其中两题我上一轮已经写成「我拍了推荐、你不反对就照走」，再拿出来问等于自己打自己脸、把已收口的又打开——跟本文件「不设门」那节（不设门、带推荐直接走）同一根。

**How to apply:**
- 「挨个问」→ 纯文本一题，带 1 个推荐和理由，停下等答；答了再问下一题
- 只问上一轮列在「真要你拍的」里的那几条；已经标「照推荐走」的不再问
- 不用 AskUserQuestion 多题表单装拍板题；那个工具留给真正的单点分叉
- **别把我自己写进 PRD 的规矩当 owner 的规矩去问他守不守**：旧 PRD 拍板记录里「其余按方案全收」批量过的条款是我提的，不是他立的（09-11「换模先过 anna」被顶：「这是你的规矩不是我的」）。他说的「跑一下」就是字面意思：能通、回了多少字

## owner 问「哪种最好」是在问我的判断，不是说「你定」

owner 对一道选择题回「一般什么最好？可以是 1/2/3」时，是在**问我的判断**，不是说「你定」。正确做法：直接答哪种最好、为什么、前提是什么，然后等他选；不要替他拍板写进计划。

**Why:** 2026-09-12 soliloquy About 页署名方式三选一，他回「一般什么最好 可以是 123」，我当成授权直接选了 1 并写进计划，被顶「但是我只是问了 哪种最好？」。答完之后他选了 2（署名 + GitHub），和我替他选的不一样。

**How to apply:** 看到「哪种最好」「一般怎么选」「你觉得呢」这类句式 → 先给结论 + 一句理由 + 成立前提，末尾一句「你选哪个」；只有他明说「你定 / 按推荐走」才替他拍。与本文件「挨个问」「不设门」两节不冲突：那两条管的是「可逆小事别问」，这条管的是「他开口问了就要给答案」。

## owner 甩截图问「好看吗/动线怪」= 要我改，不是只要评审

owner 甩自己产品的截图问「你觉得好看吗」「动线怪怪的」时，要的是改好，不是一份评审。2026-09-17 soliloquy 一晚三次：评完停手被回「你还是思考下怎么解决吧」「所以要改呀」「改了吗」；指出一个按钮问题后又被要求「你要做一遍筛查」。

**Why:** 他在实时走查自己的产品，评审意见对他没有增量，改完的页面才有。

**How to apply:** 这类提问直接按评审结论动手改（可逆 UI 改动不用等「改」字），改完给运行时截图；他点出一个具体瑕疵时，顺手把同类问题全局筛一遍再一起修。关联本文件「不设门」那节。
