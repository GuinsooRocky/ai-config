## ③ 性能调研——播放侧测法（原始设计，07-14 照此执行）

**关键前提**：jimeng 等大模型出的视频只是**原料**，规格固定不代表进浏览器的东西固定——中间必有一道我们自己的转码。**调研最硬的产出 = "该压成什么参数才能在 onlychat 里跑得动"这套转码 ladder。**

- **场景矩阵**（压力递增）：聊天流内嵌单张卡 / **列表多张卡同屏自动播（生死线，先测这格）** / 全屏看短剧 / 滚动进出视口反复挂卸。若"多张同屏自动播"跑不动 → 产品形态必须改成"只播视口中心那张，其余显示封面图"（性能反向决定产品设计）。
- **指标取数**：首帧=loadedmetadata/canplay + requestVideoFrameCallback；掉帧=getVideoPlaybackQuality()；滚动 FPS=rAF 采样 + long task；**硬解 vs 软解=chrome://media-internals 看解码器名（软解=烧 CPU=发烫，能直接枪毙某编码）**；内存增量+滚走后是否降回（查泄漏）；4G 起播时间；有没有留占位尺寸（防聊天流跳动）。
- **素材矩阵**（从用户给的那条原始视频派生）：编码 H.264/H.265/AV1/VP9 × 分辨率 540p/720p/1080p × 高中低码率；短片档(3-6s 循环)与短剧档(30s+)分开测、结论不通用；GIF/animated webp 作对照组，目的是**拿数据把 GIF 正式枪毙**。
- **设备/网络**：桌面 Chrome + 中端 iPhone + **一台真正的中低端安卓（结论只能由下限机器给）**；WiFi/4G/慢速节流；多次取中位数。
- **怎么跑**：两步走。① 独立测试页快速筛选淘汰烂格式；② **在 onlychat dev 开带开关的 demo 路由、复用真实聊天列表和卡片组件**——真正的卡顿来自我们自己的虚拟列表/重渲染，测试页测不出来，最终结论必须来自这一步。
- **开测前先定判据**（否则测完只有数字没结论）：起播出画毫秒上限、掉帧率上限、单卡资产体积上限（4G 几秒可下完）、同屏 N 张内存增量上限、低端机不发烫。
- **预判会成为分叉点的 web 卡点**（优先验证）：iOS 自动播必须静音+内联（→ 动态场景卡天然无声循环，声音只能用户点击后才有）；**同时解码路数有上限（尤其 iOS），决定"多张同屏自动播"成不成立**；iOS 低电量模式直接不给自动播 → **静态封面兜底不是可选项**；H.265 浏览器支持烂、AV1 老机器无硬解烧 CPU → 大概率回到 H.264，但要有数据支撑这个保守选择。
- **产出**：格式与码率选型表（含推荐转码参数）+ 各场景性能数据表（分设备）+ 播放策略结论（封面图先出 → 只播视口内 → 静音循环 → 滚出视口卸载 src → 短剧走全屏独立播放器）。
