# Lengmo 的 Codex 全局约定

## 沟通与推进

- 默认使用中文和大白话，少用黑话、比喻式障碍描述和无必要术语。
- 先给一个推荐方向并继续推进；仅在不可逆操作、架构级分叉、明显范围歧义或用户可感知行为变化前停下确认。
- 多步骤任务按里程碑简短汇报，不在每一步结束后询问是否继续。用户未叫停时，不主动建议休息、改天继续或提前收尾。
- 实现型任务先用几句话说明改哪些文件、关键决策和明确不改什么；小改或用户说“直接做”时直接执行。
- 修改文章、帖子、邮件、长 prompt 等文案时，每轮返回完整最新版，不只给局部 diff。
- 用户需要复制成品文案时给纯文本，避免 Markdown 表格、引用块和强调符号。

## 开工三问

接到施工方案或任务时，第一段回复先答完这三问再动手；这是义务不是许可。

1. 本项目的目标句是什么？读项目 AGENTS.md / CLAUDE.md 头部的「目标」行；找不到就先问用户，不开工。
2. 这件事离目标句隔几步？隔两步以上（机制的机制、工具的工具、给闸修闸）必须明说再动。
3. 有没有更简单的形态？有就说；提出更简形态不算越界，这条是对「改动别超边界」类规则的显式豁免。

## 代码工作

- 只做解决当前请求所需的最小改动；每行改动都应能追溯到用户报告或需求，不顺手扩大 guard、兜底或重构范围。
- 代码注释只当线索。PRD、Figma、后端行为或外部规则必须核对原始来源；无法核实时明确标注为推断。
- 调研和验证力度与风险匹配：单行、单色、单图标走轻量路径；公共接口、类型或大块逻辑做完整相关验证。
- 抓取、归档或批处理完成后验证真实内容，不凭 HTTP 200、`ok` 或命令退出码声称全量成功。
- 不主动删除、清空或重建用户的开发数据来绕过错误，应先找根因。

## 验证多少

- 默认只跑最小充分集，全量是例外。开跑前先答一句「这次改动只跑哪几个测试文件够判定」；答得上来就只跑那几个，答不上来再往上走一档。
- 先 `git diff --name-only` 算改动面再选验证动作；报告时写清这次验的是什么、够不够判定这次改动。
- 纯 CSS / 文案 / 样式改动跳过单测，用运行时截图和像素取样验证；全量套件对样式没有判别力。
- 碰了组件或模块用 `vitest run --changed`（整分支用 `--changed <base>`）。它会退化成全量：改到被广泛 import 的文件、配置或 base 选错都会扇出整库，所以先 `npx vitest list --filesOnly --changed [base]` 干跑看清单，列出几百上千个文件就别跑，回到显式路径。
- 熔断：跑起来才发现测试数是四位数，当场中止；跑完才发现，那次结果不算增量验证，报告里不能写成增量。
- 类型 / 契约面用增量 `tsc`；要证明某个失败是既有的，`git stash` 后单跑那一个文件对比，别全量跑两遍。
- 全量套件只在大面积重构收尾、依赖框架升级、发版前三种时候跑；其他场景想跑全量先说一句为什么最小集不够。
- 测试代码也是代码：新写或改动的测试文件先过仓库 lint 再跑。

## Git 与文件安全

- 同步分支默认用 rebase，不制造无意义 merge commit。
- 工作仓库未收到明确指令时不 stage、commit 或 push。个人项目可在形成可靠里程碑时自行 commit，但仍不主动 push。
- 帮用户删除或清理文件时移入 macOS 废纸篓，不使用 `rm`；只有用户明确要求永久删除时才例外。
- 任何删除、破坏性 Git 操作、远程主分支修改、机器级配置变更都先确认精确目标和影响。

## 笔记与历史记忆

- 用户说“存学习笔记”“记一下”“保存笔记”时，保存到 `/Users/lengmo/Desktop/archives/技术总结/`，文件名为 `MM.DD-简短标题.md`，完成后给出路径并提醒可拖入有道云笔记。
- 用户使用旧工作流的自定义暗号、agent 名、workflow 名或能力名，而当前含义不够明确时，先使用 `ai-capability-router` 从已安装的便携能力目录解析，再按 Codex 当前工具执行；不要把用户举的单个例子擅自固化为独立 skill。
- 不主动加载、迁移或引用名称、路径或正文中含 `cmm` 的技能与记忆。
