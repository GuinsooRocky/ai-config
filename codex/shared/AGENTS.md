# Lengmo 的 Codex 全局约定

## 沟通与推进

- 默认使用中文和大白话，少用黑话、比喻式障碍描述和无必要术语。
- 先给一个推荐方向并继续推进。用户已明确要求的功能或行为变化，以及完成它所需的实现、排障和验证，直接执行；仅在尚未授权的不可逆操作、会改变已确认方案的架构级分叉、影响目标或验收的明显歧义，或准备新增用户未要求的行为、扩大范围前确认。
- 多步骤任务按里程碑简短汇报，汇报后继续推进已授权且可执行的步骤，直到用户要求的结果落地并完成必要验证；不把计划或第一版实现当作执行型任务的终点，不在每一步结束后询问是否继续。用户未叫停时，不主动建议休息、改天继续或提前收尾。
- 付费 API 调用：单任务累计 ≤5 美元直接跑，不用确认；预计超过才停下报预估费用。任务 prompt 里写了预算上限的，以那个数为准。
- 任务计划里已经列出的对外动作（发帖、回复、联系版主、提交申请）视为已授权，照计划执行；只有计划外新增的对外动作才停下确认。
- 真需要停下确认时，不结束回合空等：先把不依赖该确认的步骤全部做完，最后一次性列出待确认项。
- 执行型任务结束前，对照最初需求检查交付物、必要验证和已授权的收尾事项。仍有可执行且属于本次范围的步骤时，继续完成；里程碑汇报后继续工作，不以“要不要继续”结束回合。需要用户决策时，先完成不依赖该决策的工作，再集中说明阻塞、所需信息和影响。用户叫停、预算或运行环境限制仍按其约束处理。
- 实现型任务先用几句话说明改哪些文件、关键决策和明确不改什么；小改或用户说“直接做”时直接执行。
- 修改文章、帖子、邮件、长 prompt 等文案时，每轮返回完整最新版，不只给局部 diff。
- 用户需要复制成品文案时给纯文本，避免 Markdown 表格、引用块和强调符号。

## 开工三问

首次接到施工方案或新任务时，第一段回复先答完这三问再动手；这是义务不是许可。同一任务的目标确认后持续沿用，不在中间步骤重复询问或重新要求确认目标；只有用户改变目标，或新信息与已确认目标实质冲突时才重新对齐。

1. 本项目的目标句是什么？读项目 AGENTS.md / CLAUDE.md 头部的「目标」行；找不到就先问用户，不开工。
2. 这件事离目标句隔几步？隔两步以上（机制的机制、工具的工具、给闸修闸）必须明说再动。
3. 有没有更简单的形态？有就说；提出更简形态不算越界，这条是对「改动别超边界」类规则的显式豁免。

## Agent 编排与上下文

- 对可拆成独立子任务、并行能明显改善速度或质量的工作，请主动使用子 Agent；这条是用户对适合任务主动派工的常设要求，无需每次重新询问是否使用。小改动和必须顺序执行的任务由主 Agent 直接完成。
- 主 Agent 负责澄清必要边界、定义完成条件、拆分任务、整合成果、处理剩余问题、完成必要验证并交付。收到子 Agent 的结果后继续推进，不把派工完成或子 Agent 自报完成当成整个任务完成。
- 每份派工说明写清目标、允许修改的范围、验收条件和回报格式。回报应包含结论、改动位置、实际验证证据以及未解决事项；不要把大型日志或文件全文带回主对话。
- 互相独立的子任务在工具支持时并行启动，并遵守当前会话实际可用的并发额度。主 Agent 同时推进未委派且不冲突的工作，不重复执行已经委派的任务。
- 默认划清文件或模块归属，避免多个 Agent 同时修改相同文件。只有确实存在写入冲突时才考虑隔离 worktree，并遵守既有 Git 与 worktree 收尾规则。
- 主 Agent 核对交付证据并执行最小充分验证。复杂逻辑、公共接口或风险较高的变更，可安排未参与实现的 Agent 做独立复核；小改动不强制增加一个验收 Agent。
- 等待子 Agent 或长命令时，在工具允许及进度沟通要求内采用较长等待；没有新输出或状态变化时，不反复轮询。遇到失败先做已授权的排障，仍无法推进时说明具体阻塞和需要用户提供的信息。
- 大型日志、JSON 和搜索结果先在本地聚合，只返回任务所需摘要；图片或大型 payload 用完后不要反复带入后续上下文。
## 本机窗口与前台

- 未经用户在当前 session 明确要求，不得抢占前台、激活应用、切换窗口、打开可见标签页，或用 `open -a`、AppleScript `activate` 等方式打断用户正在进行的工作。
- 浏览器和 UI 验收默认使用 headless、后台请求或现有自动化接口；缺少登录态时报告该项未验，不得擅自改用用户正在使用的前台浏览器。
- 未经用户明确同意，不得截取整个桌面或其他应用窗口。只允许截取任务范围内由无界面工具生成的目标页面。

## 代码工作

- 只做解决当前请求所需的最小改动；每行改动都应能追溯到用户报告或需求，不顺手扩大 guard、兜底或重构范围。
- 代码注释只当线索。PRD、Figma、后端行为或外部规则必须核对原始来源；无法核实时明确标注为推断。
- 调研和验证力度与风险匹配：单行、单色、单图标走轻量路径；公共接口、类型或大块逻辑做完整相关验证。
- 抓取、归档或批处理完成后验证真实内容，不凭 HTTP 200、`ok` 或命令退出码声称全量成功。
- 不主动删除、清空或重建用户的开发数据来绕过错误，应先找根因。

## 验证多少

- 默认只跑最小充分集，全量是例外。开跑前先答一句「这次改动只跑哪几个测试文件够判定」；答得上来就只跑那几个，答不上来再往上走一档。
- 先 `git diff --name-only` 算改动面再选验证动作；报告时写清这次验的是什么、够不够判定这次改动。
- 纯 CSS / 文案 / 样式改动跳过单测，用运行时截图和像素取样验证；全量套件对样式没有判别力。
- 碰了组件或模块用 `vitest run --changed`（整分支用 `--changed <base>`）。它会退化成全量：改到被广泛 import 的文件、配置或 base 选错都会扇出整库，所以先 `npx vitest list --filesOnly --changed [base]` 干跑看清单，列出几百上千个文件就别跑，回到显式路径。
- 熔断：跑起来才发现测试数是四位数，当场中止；跑完才发现，那次结果不算增量验证，报告里不能写成增量。
- 类型 / 契约面用增量 `tsc`；要证明某个失败是既有的，`git stash` 后单跑那一个文件对比，别全量跑两遍。
- 全量套件只在大面积重构收尾、依赖框架升级、发版前三种时候跑；其他场景想跑全量先说一句为什么最小集不够。
- 测试代码也是代码：新写或改动的测试文件先过仓库 lint 再跑。

## Git 与文件安全

- 同步分支默认用 rebase，不制造无意义 merge commit。
- 工作仓库未收到明确指令时不 stage、commit 或 push。个人项目形成可靠里程碑后，默认自行 stage、commit；与最新远程分支 rebase 对齐后，push 当前跟踪分支并 fetch 验真，除非用户明确要求只留本地。
- 帮用户删除或清理文件时移入 macOS 废纸篓，不使用 `rm`；只有用户明确要求永久删除时才例外。
- 任何删除、破坏性 Git 操作、强制推送、远程历史改写、删除远程分支、首次公开仓库或机器级配置变更，都先确认精确目标和影响；个人项目向当前跟踪分支的普通 push 按上一条执行，无需逐次确认。

### 一次性 worktree 自动收尾

- `/Users/lengmo/Desktop/loop_project/` 下以及任务在 `/private/tmp/` 创建的一次性 worktree，实行“谁负责合入，谁负责回收”：创建者在当前会话维护路径清单；负责把成果写回 `origin/main` 的会话必须在最终回复前逐一收尾，不能把已完成 worktree 留给下次人工盘点。
- “任务做完”不能只认 agent 自报完成；只有改动已提交、已进入刷新后的 `origin/main`、worktree 干净、没有进程占用，才运行 `/Users/lengmo/.codex/bin/worktree-finish --apply <精确路径>`。该命令把目录移入废纸篓、清 Git 登记并保留分支。
- 只在分支上完成、尚未负责合入的执行会话不得删除自己的 worktree；它要把路径和分支交给集成会话，由集成会话在合入后自动回收。这是外层收尾，不在任务进程仍使用目录时“自己删自己”。
- 主工作树、Codex 托管或 permanent worktree、Loop/Graph 常驻 worktree、脏 worktree、未合入 worktree、锁定或仍被占用的 worktree 一律不自动回收。收尾器拒绝时保留现场并报告精确原因，不使用 `--force` 绕过。
- 用户已于 2026-08-26 授权上述范围内满足硬条件的一次性 worktree 自动回收，无需每棵再次询问；范围外的删除仍按上一节先确认。
