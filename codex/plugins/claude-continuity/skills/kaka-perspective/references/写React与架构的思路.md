# 写 React 与架构的思路 — yangbo 的技术取舍

蒸馏自 React18 基础版、React Query、两本架构尊享版的正文。做 React/状态/架构决策时按此走。
每条是「主张 X 而不是 Y，因为 Z」。

## 一、React hooks 心智

1. **数据驱动 UI → 开关思维**：改数据的方式越简单越好，回调里最好只写一行 `setRefreshing(true)`，
   真正的逻辑交给 `useEffect` 监听依赖触发。反对在回调里直接堆请求逻辑。
2. **要基于旧值算时用函数式更新** `setCount(prev => prev+1)`，不用 `setCount(count+1)`——
   后者只能从闭包拿到上次的值，函数式更新直接从 Fiber 取最新值，绕过闭包陷阱。
3. **数据放在「共享它的最近父组件」**，不一律塞全局 store——全局状态被滥用，大项目有内存隐患；
   「不共享的数据就该组件私有」。
4. **依赖项按「实际逻辑」想，不是「用到的状态就全加」**——把 `step` 加进 deps 会让定时器每次重建。
5. **「既是状态又是逻辑值」的变量一分为二**：一个 `useState` 给 UI，一个逻辑值参与运算
   （React18 解闭包陷阱的办法；React19 才有 `useEffectEvent` 这个更简洁方案）。
6. **`useCallback` 的价值是「稳定引用」不是「省创建成本」**——函数照样每次重建；脱离 `memo` 子组件
   单用 `useCallback` 没有意义。
7. **`useMemo` 缓存「运算结果」、`useCallback` 缓存「函数引用」，按语义选**——两者能互相实现，
   但按语义选才标准。
8. **耗时计算不要塞进 `useMemo` 在渲染期同步跑**——会阻塞 UI，该异步化就异步化，别照搬官方文档。

组件长度：**人为约定 200 行（或 150 行）警戒线**，超出即拆。

## 二、状态 / 数据管理（React Query）

1. **服务端状态与客户端状态彻底分离**——服务端数据不进 Redux/Zustand（否则要手写大量
   Action/Thunk/Saga 样板）；模态框、表单值这类 UI 状态才归 `useState`/Context/Zustand。
2. **用 React Query 取代 useEffect 手写请求**——手写要管三个状态 + 竞态 + 卸载后报错；
   React Query 一行搞定，自带重试。
3. **依赖查询用 `enabled` 控制，不用嵌套请求**——先拿到 id，`enabled: !!id` 再触发下一个。
4. **高频低失败操作用乐观更新**（点赞），实时性要求不高的用传统等待。乐观更新标准流程：
   `onMutate`（取消查询 + 存快照 + 改缓存）→ `onError`（回滚）→ `onSettled`。
5. **乐观更新成功后用「服务端返回数据精确更新缓存」**，不用 `invalidateQueries` 重拉——
   重拉会导致动画重播；只在失败时才 refetch。

## 三、架构方法论

1. **总分总顺序**：动手前先吃透设计稿的「布局 + 交互 + 数据逻辑」，先整体后细节，最后组合。
   反对「一上来就写页面，写到一半发现拆不下去」。
2. **四层数据架构**（他的 `SKILL.md` 模板）：
   `api.ts`（与后端 1:1，不做逻辑）→ `service.ts`（多接口聚合，并行 `Promise.all`、依赖 `await`，
   导出唯一数据源）→ `controller.ts`（Zod 校验 + 字段补全 + 格式转换，产出「完美数据」）→
   `index.tsx`（纯 View）。
3. **单一数据入口**：一个 View 只能有一个数据获取入口，要多个就先拆组件。
   View 层禁止在 JSX 里写 `?.`/`|| ''` 防御性代码——那是 controller 的活。
4. **拆分三标准**：① 目的是可读性/可维护性，复用只是其一；② 200 行警戒线；
   ③ 拆出来必须能提炼出**明确语义**——提炼不出语义就是拆得不合理。
5. **Loading 与组件一对一**：Loading 个数由交互设计定，与接口个数无关。两个 API 合成一个列表
   只设一个 Loading，差异由 service 层抹平。
6. **嵌套思维 / 模糊化降复杂度**：思考应用层时主动模糊掉数据层复杂度——「复杂的可能不是代码，
   而是你思考问题的复杂度」。反对超前思考，一层层解决。
7. **业务内聚（DDD 落前端）**：先按代码功能分层；某层文件过多时按**业务领域**重新归类，
   让每个业务系统能单独剥离。原则：上层依赖下层，下层不依赖上层。
8. **版本升级 = 同一架构换数据层**：React18 用 `useQuery`+`useState`；React19 改 `Promise 存
   useState`+`use`+`Suspense`。架构不变，只换异步实现，不推翻重来。

核心论点：**组件化内聚 ≈ DDD 业务内聚**——「优秀的架构设计殊途同归，不分前后端」。

## 四、新增边界（他不做什么）

- **不做超前思考**——先把当前层搞定，主动模糊下层复杂度。
- **不为复用而拆分**——拆的标准是「后期维护能否不用过多关注」，不是「能否复用」。
- **不滥用全局状态**——服务端数据不进全局 store；客户端状态优先组件自管。
- **不照搬官方文档**——反对官方「`useMemo` 缓存耗时计算」在渲染期同步跑。
