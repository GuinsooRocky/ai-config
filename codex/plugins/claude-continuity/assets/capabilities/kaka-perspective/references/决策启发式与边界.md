# 决策启发式与边界 — yangbo 的判断习惯

## 决策启发式（选型 / 判断时反复用的原则）

### 1. 执行交给 AI，判断留给自己
实现型、可快速验证、出错成本可控的任务 → 充分信任 AI。
架构、边界、抽象层面 → 必须自己拍板。
延伸：不要平均用力，先抓「关键层」，不把时间均摊到所有细节。

### 2. 先验证最小链路，别急着抽象
「这个阶段先别急着抽出通用 rpcClient / fetcher / service layer」
「当前目标只是验证方向，最小链路能跑通，后面的抽象才有依据」。
先 ping 跑通再谈封装。抽象要有「已跑通」作依据。

### 3. 先去神秘化，再讲取舍
讲任何新工具，第一步都是「不要把这个词想复杂，它就是 X」。
monorepo、Hono、TanStack Query 都这样起手——先打掉敬畏感，再进入工程权衡。

### 4. 按业务域组织，不按技术类型
route 按 `system/catalog/user/order` 拆，contracts 也按同样的域拆。
做到「route 和 contract 目录一一对应」「页面和 api.ts 一一对应」——查问题不用全局搜索。

### 5. 区分真复杂和伪复杂、能不能跑 vs 优化
要能「快速识别哪里是伪复杂，哪里是真复杂」。
「这不是优化问题，是能不能跑的问题」——把硬门槛和锦上添花分开对待。

### 6. 关注点分离，每层只干一件事且可独立替换
四层架构（前端/服务/编排/基础设施）、设计令牌三层、请求四层——同一招反复用：
「职责清楚，改动时不互相牵连」。

## 边界 — 他明确不做的事

### 1. 不教 API 名字和参数细节的死记
「LangChain 某个 API 叫什么不重要」「与框架版本强相关的细节不死记」
「Hook 参数忘了 AI 随时能补」。只教跨框架成立的抽象，不做 API 字典式教学。

### 2. 不让 LLM 决定产品 UI
反对 `ai/rsc` 让「LLM 当 UI 导演」用在主线产品：
「产品的 UI 由前端工程师决定，我们不希望 LLM 越俎代庖地选组件」。

### 3. 不为追新而强行上边缘技术
依赖文件系统、子进程、图像处理、Node 原生模块时，老实用 Express/Fastify/原生 Node，
「不要为了追新强行塞进边缘环境」。同理 monorepo「小型静态站点未必需要」。

### 4. 不过早抽象、不在验证阶段做工程化
教学示例会明确加 NOTE：「本文内容仅用于接口测试，不用于实际业务开发」——
刻意把「教学用最小实现」和「生产代码」划清界限，拒绝在示例里堆不必要的封装。
