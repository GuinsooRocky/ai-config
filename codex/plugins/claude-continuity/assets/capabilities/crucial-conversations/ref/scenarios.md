# 场景细则：四类高利害沟通的范例校准

每类：典型坑 → 坏例/好例 → 场景特有检查点。改写时贴着用户原话的语气，范例只校准结构。

## 一、报坏消息（线上问题 / 进度延误 / 搞砸了）

**典型坑**：两个极端——把推断当事实报，制造假警报；或者捂到最后一刻才说，错过所有补救窗口。

**坏例**：
> 线上挂了，得马上回退！

结论 + 行动指令，零事实。如果判断错了，信用双倍受损（错报 + 引发无谓动作）。

**好例**：
> 线上 X 页面在报错（日志/截图：…），影响范围我还在确认。Y 是一种可能原因，还没验证。先同步现象，10 分钟后给结论。

**场景特有检查点**：
- 每个结论标了证据强度吗：亲眼验证过的 / 从 X 推断的 / 听说的
- "还没验证"的部分标出来了吗
- 给了下一次同步的时间点吗——坏消息最怕的不是坏，是断联
- 数字类结论（影响多少、几个提交）用的是全量统计还是截断输出

## 二、顶回（不同意方案 / 不同意安排）

**典型坑**：当场憋住、执行时用脚投票；或者把"我不同意这个方案"说成"这方案不行"（对事的分歧滑成对人的否定）。

**坏例**：
> 这个方案有问题，X 场景根本跑不通。

**好例**：
> 目标我理解是 Y（先对齐）。我担心 X 场景跑不通，因为（事实/数据）。如果改成 Z，能不能同时保住 Y？

**场景特有检查点**：
- 先复述了对方的目标吗——表明你是听懂了才反对的
- 对比法用了吗："我不是不想接这个活，我是担心X"
- 给替代案了吗——没有替代案的顶回读起来就是抱怨
- 分歧锚在目标上还是方案细节上——锚目标才有得谈，锚细节容易变成互相挑刺

## 三、指出别人的问题（审 PRD / 审代码，产出会被当事人看到）

**典型坑**：书面审查天然显得居高临下；批量列问题时夹带对人的定性。

**坏例**：
> 这里考虑不周，空态没处理。

**好例**：
> 这里空数据时会白屏（复现路径：…）。X 场景是预期内吗？

**场景特有检查点**：
- 只说事实 + 影响，没定性人（"漏了空态处理，用户会看到白屏" ≠ "考虑不周"）
- 每条问过自己"这会不会是对方的有意决策"吗——很多"bug"其实是你没看到的拍板；提问式（"是预期内吗？"）给对方留"是故意的"的出口
- 按严重度排序了吗；拿不准的放"待确认"区了吗，别混进"问题"区壮声势
- 整体读起来是搭把手还是审犯人

## 四、要东西（要权限 / 要资源 / 要拍板）

**典型坑**：只说"我要"，不说给了能换来什么、不给会卡住什么；要拍板时丢开放题把活扔回去。

**坏例**：
> 这事得你拍个板，你看怎么办？

**好例**：
> 现在卡在 X（事实）。两个选项：A，代价是…；B，代价是…。我倾向 A，因为…。你拍一个，我今天就能继续。

**场景特有检查点**：
- 结构齐了吗：卡在哪（事实）→ 需要什么（具体）→ 给了之后什么时候交付什么 → 不给的 plan B 和代价
- 需求具体到能直接执行吗——要权限 = 哪个系统哪个级别；要人 = 多少人天干什么
- 要拍板的，选项收敛到 2-3 个、各带代价、自带倾向了吗
