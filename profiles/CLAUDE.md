# Lengmo 的 Claude 全局约定

## 开工三问

接到施工方案或任务时，第一段回复先答完这三问再动手；这是义务不是许可。

1. 本项目的目标句是什么？读项目 AGENTS.md / CLAUDE.md 头部的「目标」行；找不到就先问用户，不开工。
2. 这件事离目标句隔几步？隔两步以上（机制的机制、工具的工具、给闸修闸）必须明说再动。
3. 有没有更简单的形态？有就说；提出更简形态不算越界，这条是对「改动别超边界」类规则的显式豁免。

## 沟通与推进

- 默认使用中文和大白话，先给推荐方向并继续推进。
- 只在不可逆操作、架构级分叉、明显范围歧义或用户可感知行为变化前停下确认。
- 多步骤任务按里程碑简短汇报，不反复询问是否继续。
- 实现型任务说明要改什么、关键决策和明确不改什么；用户说“直接做”时直接执行。

## 代码工作

- 只做当前请求需要的最小改动，不顺手扩大 guard、兜底或重构范围；每一行改动都能追溯到用户的原始请求。
- 注释只当线索；外部规则和产品事实核对原始来源，无法核实时明确标注为推断。
- 调研与验证力度匹配风险，批处理后检查真实内容，不凭退出码声称全量成功。
- 不删除或重建用户开发数据来绕过错误，先找根因。

## 验证多少

- 默认只跑最小充分集，全量是例外。开跑前先答一句「这次改动只跑哪几个测试文件够判定」；答得上来就只跑那几个，答不上来再往上走一档。
- 先 `git diff --name-only` 算改动面再选验证动作；报告时写清这次验的是什么、够不够判定这次改动。
- 纯 CSS / 文案 / 样式改动跳过单测，用运行时截图和像素取样验证；全量套件对样式没有判别力。
- 碰了组件或模块用 `vitest run --changed`（整分支用 `--changed <base>`）。它会退化成全量：改到被广泛 import 的文件、配置或 base 选错都会扇出整库，所以先 `npx vitest list --filesOnly --changed [base]` 干跑看清单，列出几百上千个文件就别跑，回到显式路径。
- 熔断：跑起来才发现测试数是四位数，当场中止；跑完才发现，那次结果不算增量验证，报告里不能写成增量。
- 类型 / 契约面用增量 `tsc`；要证明某个失败是既有的，`git stash` 后单跑那一个文件对比，别全量跑两遍。
- 全量套件只在大面积重构收尾、依赖框架升级、发版前三种时候跑；其他场景想跑全量先说一句为什么最小集不够。
- 测试代码也是代码：新写或改动的测试文件先过仓库 lint 再跑。

## 模型调度与判断

- 派子 agent、选 model、验收升降级前先读 `~/.claude/model-dispatch.md`。
- 某个动作会往主对话灌大段“只需要结论”的内容（读大文件、扫日志、长命令输出）时，派子 agent 只收结论。
- 拿不准“算不算完成 / 该不该问用户 / 该不该换路”查 `~/.claude/judgment-rubrics.md`。
- 派工 prompt 套 `~/.claude/delegation-templates.md` 的模板。
- 改以上制度文件前，先读 `~/.claude/harness-maintenance.md` 的权限分层。

## Git 与文件安全

- 同步分支默认使用 rebase。
- 未明确要求时不 stage、commit 或 push。
- 删除或清理文件时移入 macOS 废纸篓，不永久删除。
- 删除、破坏性 Git、远程主分支修改和机器级配置变更前确认精确目标与影响。

## 能力加载

- 根据当前任务使用相关 skill，不在会话开始时读取全部能力说明。
- 账号凭证、OAuth、原始会话、本机数据库和外部服务配置属于机器状态，不从 ai-config 推断。
- 不主动加载、迁移或引用名称、路径或正文中含 `cmm` 的技能与记忆。
